## Context

See proposal.md for motivation. Current state:

- The repo-local commands (`.claude/commands/challenge.md`, `synthesize.md`) delegate to subagents (`.claude/agents/challenger.md`, `synthesizer.md`). The challenger body is a verbatim copy of `config/challenge_phase_prompt.md`, held in sync by `scripts/test_challenge_agents.py`.
- The synthesizer reads `config/persona_collaboration_framework_v2.md` and the Phase 2 section of `config/challenge_synthesis_protocol.md` by repo-relative path, plus a domain `context_configuration.json` path passed by the caller.
- The plugin (`plugin/`) already bundles a generated catalog. `scripts/build_persona_index.py` writes it and `--check` (run in CI) fails on drift.
- Verified on this machine (CLI, headless): in a plugin, `${CLAUDE_PLUGIN_ROOT}` is substituted in both command bodies and agent bodies, and a plugin agent can read a file under it. UNVERIFIED: the desktop app and other CLI versions.

## Goals / Non-Goals

**Goals:**
- An installed plugin runs both phases with no checkout of this repository.
- One source of truth per file; plugin copies are generated and drift fails CI.

**Non-Goals:**
- No change to the protocol, the phase prompt or the repo-local commands and agents.
- No marketplace or plugin-manifest redesign beyond a version bump.
- No domain-activation mechanism (a separate open item).

## Decisions

1. **Generate, do not hand-copy.** The generator that writes `plugin/catalog/` also writes `plugin/framework/` and `plugin/agents/`, and `--check` compares them. Alternative: a separate sync script. Rejected: two commands to remember, and CI already runs the generator's `--check`.
2. **Commands are hand-written plugin files, not generated.** They differ from the repo-local ones by design (no `config/` paths, framework directory passed to the agent, first-principles fallback), so a text transform would be fragile. A test asserts the plugin and repo-local commands stay structurally aligned (same subagent names, same pass-only-these-inputs rules). Alternative: generate by string substitution. Rejected for fragility.
3. **The command passes the framework directory to the synthesizer.** The command body uses `${CLAUDE_PLUGIN_ROOT}/framework` and includes it in the subagent prompt as `framework_dir`; the agent reads from that path. This does not depend on agent-body substitution, which is only verified on the CLI. Alternative: put `${CLAUDE_PLUGIN_ROOT}` in the agent body. Rejected as the primary mechanism, though it works on the CLI.
4. **The plugin challenger body equals the repo-local one byte for byte** (it embeds the phase prompt and reads nothing), so it is generated by copying. The plugin synthesizer differs from the repo-local one only in how it learns file locations (`framework_dir` instead of `config/`) and the no-domain fallback, so it is generated from a template with the repo-local file as the shared source of the rules text. The drift test pins both.
5. **Domain context is an explicit input, not inferred.** The repo-local command says to identify the "active domain" from the loaded configuration, which in practice means the model guesses; an installed plugin has no loaded configuration at all. The plugin commands take `--focus` (verbatim text, the manual path) or `--domain` (lookup), else first-principles. `challenge_focus` is a short label authored once per domain in its `context_configuration.json` (for example `architecture_goals_and_software_correctness`); the commands look it up and never compose it. It is an interrogation axis, not subject-matter expertise, which lives in the personas.
6. **Inheritance follows the repo's existing layering.** Project-level configs (`hero_heaven`, `screenplays`) declare they "extend/override" the domain-level config and carry a `merge_behavior` note. `domains.json` therefore gives a project the domain's `challenge_focus` unless it declares its own. "Parent" means the domain-level config in the nearest enclosing `personas/<domain>/` directory, nothing more.
7. **The synthesizer gets the lens, not a config path.** Alternative: also pass the config so it can use the persona roster. Rejected for the plugin: configs are not bundled, and the roster depends on the unspecified domain-activation mechanism. Known limitation: plugin synthesis runs without a domain roster; the repo-local path keeps it.
8. **`domain_context` becomes optional in the protocol.** It is marked required while the phase prompt defines a fallback and R-2 requires manual orchestration to work; the two disagreed.
9. **Plugin version bump** to 0.2.0: the exposed surface grows.

## Risks / Trade-offs

- [The synthesizer template drifts from the repo-local agent's rules] → the drift test compares the shared rules section.
- [Agent-body `${CLAUDE_PLUGIN_ROOT}` is untested on the desktop app] → the design does not rely on it (Decision 3).
- [Plugin agents named `challenger` / `synthesizer` clash with repo-local ones when the plugin is installed inside this repo] → plugin agents are namespaced (`tif:challenger`); the commands name them explicitly. Verify in task 4.
- [An installed plugin lives in a cache directory outside the project; a subagent's Read there may prompt or be blocked by the desktop app or a sandbox, which headless CLI testing did not exercise] → task 4.6 checks the desktop app; if blocked, document the permission the user must allow.
- [Bundled files add maintenance surface] → generated and checked, same as the catalog.

## Migration Plan

Ship in one PR. No data migration. Rollback is reverting the PR; the plugin version bump makes the change visible to installers.
